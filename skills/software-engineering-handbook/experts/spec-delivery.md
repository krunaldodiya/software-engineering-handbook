# Specification-delivery experts

Use only when the canonical router selects durable specification artifacts,
cross-artifact consistency, or a revisioned change packet. A clear localized
task should use its governing issue and changed-path evidence instead. This
fallback never activates a provider framework or installer.

## Right-size the artifact chain

Create only artifacts that carry a current decision across a real boundary such
as multiple sessions, contributors, repositories, public contracts, or R3–R4
review. A complete chain may include governing principles, specification,
design, plan, tasks, evidence, and accepted canonical requirements. Omit a layer
when the same contract is already authoritative elsewhere.

## Principles and change packet

`spec-kit`'s constitution capability maps to existing project and repository
rules. Read and reconcile those sources; do not generate a competing
constitution.

A change packet has a stable identity and base revision. It records intent,
outcomes, non-goals, requirements and scenarios, design decisions, dependency
order, tasks, acceptance evidence, status, and unresolved decisions. Keep
product requirements separate from implementation choices.

## Explore and assess

Spec Kit assessment skills (`speckit-assess-intake`,
`speckit-assess-research`, `speckit-assess-define`, `speckit-assess-shape`,
`speckit-assess-decide`) and OpenSpec `openspec-explore` are read-only discovery
paths. Capture supporting and opposing evidence, the user problem, success
measures, alternatives, and a `go`, `clarify`, or `stop` decision. Exploration
must not silently become implementation.

## Specify and clarify

`spec-kit`'s `speckit-specify` and `speckit-clarify`, plus OpenSpec
`openspec-propose`, define observable behavior before implementation. State
actors, outcomes, positive and negative scenarios, boundaries, unsupported
cases, non-goals, acceptance evidence, and unresolved decisions. Clarify only
consequential ambiguity that current evidence cannot resolve.

OpenSpec-style deltas mark requirements as added, modified, or removed. A
modified requirement carries its complete new contract, not a fragment that
loses retained behavior.

## Plan, tasks, and issues

`speckit-plan` records the minimum technical decisions needed to satisfy the
specification. `speckit-tasks` produces dependency-ordered, independently
verifiable slices. Include the highest stable test seam, migration or rollback
boundary, and exact acceptance evidence for each consequential slice.

`speckit-taskstoissues` is an external tracker effect. It may run only when the
user or project authorizes the exact repository, task set, and labels; planning
alone never authorizes publication.

OpenSpec `openspec-new`, `openspec-continue`, and `openspec-ff` create or advance
only the requested artifacts. Fast-forward may skip interaction, never required
analysis, authority, or evidence.

## Analyze and checklist

`speckit-analyze` checks requirements, design, plan, and tasks for contradictions,
missing coverage, dependency errors, and invented scope. `speckit-checklist`
challenges specification quality: clarity, completeness, consistency,
measurability, failure behavior, and traceability. A checklist is not behavioral
proof and must not become a fixed universal template.

## Implement, verify, and converge

`speckit-implement` and OpenSpec `openspec-apply` execute only accepted tasks
under ordinary handbook controls. OpenSpec `openspec-verify` and
`speckit-converge` compare the candidate against requirements, design, tasks,
and runtime evidence. They append or correct concrete remaining work; they do
not redefine acceptance to match the implementation.

The Spec Kit bug extension maps to the handbook debugging contract:
`speckit-bug-assess` establishes reproduction and root cause,
`speckit-bug-fix` changes the shared cause, and `speckit-bug-test` exercises the
original symptom and relevant regression boundary.

## Archive and canonicalize

OpenSpec `openspec-archive` may merge an accepted delta into canonical specs only
after implementation, evidence, and acceptance are tied to exact bytes.
`openspec-bulk-archive` additionally requires conflict-free ordering among every
change. Archive retains provenance and history; it does not hide abandoned or
failed work. `openspec-onboard` is read-only orientation to existing specs.

## Effects and evidence

This fallback does not install CLIs, initialize repositories, add hooks,
telemetry, dashboards, stores, presets, extensions, bundles, publish issues, or
commit generated artifacts. Those are separate authorized tool and supply-chain
actions. Its output is a bounded artifact set plus a consistency and convergence
result grounded in the governing sources and exact candidate revision.
