# Engineering handbook enforcement

For non-trivial implementation, review, testing, debugging, delivery, operation, or maintenance work, read `skill://software-engineering-handbook` before acting and apply the relevant handbook chapters.

Use the handbook skill as the only workflow-level router. No external skill pack
is required. Resolve compact descriptors before loading bodies, activate the
smallest compatible expert set within the risk-scaled budget, and use either one
trusted matching original or its complete internal fallback. Never load the full
catalog or both implementations of one semantic purpose.

System and user instructions plus explicit product, domain, repository, and executable-gate requirements take precedence over generic handbook defaults. A local conflict that would weaken safety, authorization, privacy, security, evidence integrity, or a regulated control must be surfaced and resolved by an authorized owner; never silently waive it.

Use the cheapest process that produces evidence proportionate to risk. Do not invent project commands, mandatory frameworks, review staffing, coverage thresholds, branch policies, sprint lengths, or tracker taxonomies when the active project has not defined them.

For coding work, understand the affected flow, reject speculative work, reuse
the repository, prefer the standard library, then native platform features,
then an already approved dependency, and only then write the smallest direct
implementation. This economy must not reduce required scope, correctness,
safety, accessibility, error handling, or evidence.
